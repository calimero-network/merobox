`workflow-examples/cloud-v2/` holds the examples. CI runs all five against
core's `release-v2` branch (job `test-cloud-v2`), and core's own e2e runs them
against every core change.

| Workflow | What it shows | Needs |
| --- | --- | --- |
| `kv-store-failover.yml` | A crash, a frozen node and a restart; replicas catch up | `KV_STORE_WASM` |
| `frozen-leader.yml` | The app's leader stops answering; writes reroute within a 10 s budget | `KV_STORE_WASM` |
| `orgs-and-keys.yml` | Organizations gate apps, scoped API keys, passkey confirmations, removal | `KV_STORE_WASM` |
| `packages.yml` | Signed releases installed from the registry, verified on every node, upgraded by version, uninstalled | `KV_STORE_MPK`, `KV_STORE_MPK_NEXT` |
| `rolling-upgrade.yml` | Every node moved to another build in turn while the app keeps its data | `KV_STORE_WASM`, `MEROD_V2_BINARY`, `MEROD_V2_UPGRADE_BINARY` (a different build) |

Building the inputs, from a core checkout on `release-v2`:

```bash
cargo build -p merod
cargo build -p kv-store --target wasm32-unknown-unknown --profile app-release
# two signed releases of one package, for packages.yml
(cd apps/kv-store && cargo mero bundle --dev --no-icon --app-version 1.0.0)
(cd apps/kv-store && cargo mero bundle --dev --no-icon --app-version 1.1.0)

export MEROD_BINARY=$PWD/target/debug/merod MEROD_V2_BINARY=$PWD/target/debug/merod
export KV_STORE_WASM=$PWD/target/wasm32-unknown-unknown/app-release/kv_store.wasm
export KV_STORE_MPK=$PWD/dist/com.calimero.kv-store-1.0.0.mpk
export KV_STORE_MPK_NEXT=$PWD/dist/com.calimero.kv-store-1.1.0.mpk
export MEROD_V2_UPGRADE_BINARY=…   # another merod build; the same binary refuses to pass

for wf in workflow-examples/cloud-v2/*.yml; do merobox cloud run "$wf"; done
```

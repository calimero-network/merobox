A release-v2 cluster is one service: `merod` nodes replicate every app by Raft,
and people reach it as clients (passkeys, API keys) rather than running nodes.
merobox starts such a cluster on one machine, one process per node, so a
workflow can crash, freeze, restart and upgrade nodes, and drives it through
calimero-client-py's `CloudClient`.

## The pieces

| Module | Role |
| --- | --- |
| `merobox/cli.py`, `merobox/commands/cloud.py` | The CLI: `merobox cloud run|validate|port`, and v1's names `merobox bootstrap run|validate` and `merobox run`, which route to them |
| `merobox/cloud_v2/workflow.py` | `load_workflow` checks a file against `STEP_TYPES`; `Runner` signs up the accounts and runs the steps; `run_workflow_outcome` wraps a run in a cluster's lifetime |
| `merobox/cloud_v2/cluster.py` | `ProcessCluster`: N `merod run --dev` processes on `127.0.0.1:base_port+i`, each with its own data directory, told about each other by `--peers`; `PackageRegistry`, a local registry that `install_package` publishes signed `.mpk` releases to |
| `merobox/cloud_v2/assertions.py` | The `assert` and `json_assert` steps |
| `merobox/cloud_v2/port.py` | `merobox cloud port`: v1 workflow → cloud-v2 workflow |

## A run

1. `load_workflow` reads the file, requires `backend: cloud-v2`, and checks
   every step's type and required fields.
2. `ProcessCluster.start` launches the nodes and waits until each answers
   `/health` and the system group has a leader.
3. `Runner` signs each account up with its own software passkey, then runs the
   steps in order. A step acting as an account uses that account's node first
   and the others after it, so a node failure does not fail the step.
4. Whatever happens, the cluster is stopped and, unless `--data-dir` was
   given, its state removed.

Faults are process signals: `kill_node` is SIGKILL (a crash), `pause_node` is
SIGSTOP (a node that is unreachable but not gone), `restart_node` starts a node
again on its data, optionally on another binary (a rolling upgrade).
